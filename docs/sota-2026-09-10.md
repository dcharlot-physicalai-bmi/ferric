# What to build next, ranked by what people actually download

**Method.** Every claim here is anchored to one of two things: a download count from the Hugging Face
API (top 120 GGUF repos, 141,987,186 downloads, pulled 2026-09-10) or an arch string read out of a
**real GGUF header** by range-requesting the first 8 KiB of the file. Nothing is ranked by
architecture count. Nothing is taken from a model card.

⚠ **Two false readings were caught by insisting on the header, and both would have changed the
ranking.** `gemma-4` first came back as `gemma4-assistant` — that file was the `MTP/` *draft* model,
while all three real gemma-4 repos say `gemma4`, which Ferric has. That error alone would have
invented a 10.2% gap. `Inkling` and `Qwen3.8-Flash-Next` first came back as `clip` — that was the
`mmproj` vision tower, not the text model. Read the neighbouring artifact, get a confident wrong
answer; the same shape as `ffn_out` vs `ffn_moe_out`.

## The techniques the corpus is actually shipping

Measured as download share of the same top-120:

| technique | share | Ferric |
|---|---|---|
| **MTP / multi-token prediction** | **7.5%** | qwen35 ONLY |
| **QAT checkpoints** | **5.6%** | format-transparent, runs |
| **NVFP4** (ggml type 40) | **1.7%** | ⛔ ABSENT |
| MXFP4 (type 39) | 0.0% by name | supported |

### 1. NVFP4 — the cheapest real win

`GGML_TYPE_NVFP4 = 40` merged into llama.cpp over Mar–Apr 2026 with CUDA, SYCL and Vulkan paths.
Geometry: **16 values per block, two-level scale** — an FP8 (E4M3) scale per block plus one FP32
scale across the whole tensor. That second level is the part MXFP4 does not have and the reason a
naive port of the MXFP4 kernel will be silently wrong rather than merely slow.

Ferric's `QMatrix::block_bytes` has 39 (MXFP4, 32/17) and **no 40**. One repo in the top-120 already
ships it (`cdiamond/Qwen3.8-27B-iMatrix-NVFP4-MTP-GGUF`, 2.48M). This is a bounded, self-contained
addition: a block geometry, an unpack, and a matmul that already has five siblings to copy.

### 2. MTP is implemented but reaches one architecture

llama.cpp merged MTP in May 2026 (`--mtp`, off by default) and a community benchmark reported
Qwen3.6-27B going 38 → 65 tok/s on a 5090, **1.71x** at Q4_K_M.

Ferric already does this — `qwen35.rs` implements the `nextn` draft block
(`eh_proj(cat[enorm(embed(t+1)), hnorm(hidden)])`) and `ferric-serve` runs it. ⭐ **And Ferric is
AHEAD of the field in one specific way**: `specgate.rs` derives the acceptance rate at which
speculating is worth its energy — `a > E_d / E_m` — and refuses below it. No other runtime surveyed
prices speculation in joules; llama.cpp's flag is on/off.

⛔ **But `grep -ci mtp` across `crates/ferric-llama/src/` matches ONE file.** `gemma4` ships MTP
weights and is 10.2% of downloads.

⚠ **AND "generalise the loader" UNDERSTATES THE WORK — corrected after reading gemma4's MTP header.**
It is a different dialect, not the same block in another file:

| | qwen35 `nextn` | gemma4 `gemma4-assistant` |
|---|---|---|
| container | last layers of the SAME gguf | a SEPARATE file, its own arch string |
| depth | 1 draft block | **4** (`nextn_predict_layers = 4`) |
| width | main width | **1024**, against the main model's 3840 |
| projection | `eh_proj(cat[enorm(embed), hnorm(hidden)])` | `pre_projection [7680,1024]` -> blocks -> `post_projection [1024,3840]` |
| draft KV | its own cache | ⭐ **`attn_q` only — NO `attn_k`/`attn_v`**, so it reuses the main model's KV |
| per block | — | `layer_output_scale [1]`; `blk.3` is twice as wide as `blk.0..2` |

`7680 = 2 x 3840`, so `pre_projection` eats a concatenation of two main-width vectors — the same
*shape* of idea as qwen35's `eh_proj`, at a different width and depth, in a different container.
So a general MTP needs an abstraction over four axes (container, depth, projection, KV sharing), not
a loosened tensor-name match. Still ranked #1 on value; it is a port, not a refactor.

⭐ **This also un-retracts `gemma4-assistant`.** Above, it is called a false gap — correct for MAIN
MODEL coverage, since real gemma-4 checkpoints say `gemma4`. But it is a REAL arch that Ferric would
need registered to run gemma4 speculation. False gap for coverage, true gap for the draft path.

## The performance item, stated as one number

Same kernel, same fabric, quiet machine (load 3.84):

| | GB/s |
|---|---|
| one 176 MiB weight, streamed | **255.0** |
| the same total bytes as many small distinct weights | **38.9 – 68.0** |

A **3.7–6.6x penalty purely from splitting the stream into many small matmuls.** Whole-model Ferric
is 67 GB/s against llama.cpp's 156 on the same checkpoint — so whatever llama.cpp does differently,
it does it here, and the remaining 2.33x lives in this row and nowhere else.

⚠ Two things this is NOT, both checked rather than assumed:
- **Not host overhead.** `run_ids` reports host-side setup at 8.1% of wall (pipeline lookup 2.91 ms,
  bind groups 4.38, recording 0.30, submit 0.56, of 100.8 ms). 92% is GPU.
- **Not the submit floor.** The control measures a per-submit floor of ~60 us that is indifferent to
  bytes: `rmsnorm [1,4096]` reading 16 KiB costs 59.5 us, `matmul_q` reading 176 KiB costs 63.9 us —
  11x the data, 7% more time. The model issues 310 dispatches in 29 submits per token (10.7:1), so
  it pays that floor 29 times, not 310.

## The one place cross-fabric identity costs measurable speed

`MATMUL_Q4_K_SGGEMV_WGSL` exists — one subgroup per output, `subgroupAdd` instead of a shared-memory
barrier — and is deliberately opt-in behind `FERRIC_SGGEMV` because **subgroup reduction order is
hardware-dependent and would break bit-identity across adapters**. Same for coop_matrix. llama.cpp
makes no identity promise and uses simdgroup reductions freely.

⚠ **The exchange rate is currently UNKNOWN and should not be guessed.** The kernel exists only for
Q4_K, reuses the FLAT weight buffers, and `matmul_q` does not route the FFN (that goes through
`try_matmul_swiglu`), so measuring it today would price a fraction of the graph. Pricing it honestly
needs a Q5_K subgroup kernel and a subgroup SwiGLU variant. Worth doing deliberately: if determinism
costs 1.5x, that belongs in the README as a documented flag, not discovered by a user.

## Where the browser lever is

LlamaWeb (arXiv 2605.20706) reports up to **69% throughput gain** on WebGPU and attributes its weak
prefill to *the absence of kernel fusion and subgroup matrix ops in the browser path*. Ferric has the
fusion (`qk_norm_rope`, `matmul_q*_swiglu`, `add_rmsnorm`). WebGPU **subgroup matrix** is not in
stable browsers yet; W3C discussion is ongoing. Ferric's `coop_matrix` is native-gated (Vulkan +
Metal 4 MPP), so the browser path inherits it the day the feature stabilises — provided the kernel is
written against the WGSL type and not against MPP directly.

## Ranked

1. **MTP past `qwen35`** — 7.5% of downloads ship MTP weights; 1.71x where it applies; the energy
   gate is already built and is a genuine differentiator. ⚠ Costed as a PORT (four axes differ), not
   the refactor this line first claimed.
2. **NVFP4 (type 40)** — bounded work, already in the corpus, and the two-level scale makes a naive
   MXFP4 port silently wrong.
3. **The split-stream penalty** — the entire remaining 2.33x, isolated to one measurable row.
4. **Arch ports in download order** — `deepseek4-dspark`, `qwen3vl`, `inkling`, `qwen4exp`, `chatglm`.
5. **Price the determinism trade** — needs a Q5_K subgroup kernel first; do not quote a number before.

## On "open weights will win because software will win"

The download data is consistent with the thesis and sharpens it. 141,987,186 downloads across 120
repos, and the top of the list is not a frontier lab's API — it is `unsloth`, `ornith-ai`,
`lmstudio-community`, `bartowski`, `mudler`, and a long tail of community requantisations of the same
few base models. **The base weights are a commodity; the packaging is where the volume is.** Eleven
of the top 120 ship MTP draft heads and 5.6% are QAT checkpoints — the corpus is now shipping
*runtime-facing artifacts*, not just weights, which is precisely the surface a runtime competes on.

⭐ Ferric's defensible position is not tok/s, which llama.cpp will keep contesting. It is the two
things nothing else on this list has: **one graph that is bit-identical across fabrics**, and **an
energy model that can refuse work that does not pay for itself**. Both are software, and both get
harder to copy the longer they run.
