# FERRIC INGEST LIST — ranked by value / effort on a wgpu-WGSL, on-device-first runtime

Verified against the tree at `/Users/dcharlot/vibe-coding/ferric` (not against the capability blurb, which is stale in two places: speculative decoding and sampling-beyond-greedy both already ship).

## 1. DO NEXT

### 1.1 Split-KV (flash-decoding) in `fused_decode_attention` — **small effort, highest ratio**
**What.** Partition the KV axis across workgroups and combine partial online-softmax accumulators in a second pass. From candle PR #3655's splitkv structure; none of its CUTLASS `.cu` ports, only the shape.

**Why Ferric specifically.** `crates/ferric-tensor/src/lib.rs:530-541` dispatches `(nh, 1, 1)` — one workgroup per query head, 128 threads — and the KV loop is *serial inside* the workgroup (`for c0 = 0; c0 < s; c0 += 2048`). A 16-head model at 32k context = 16 workgroups each walking 16 chunks in sequence. That is the exact on-device profile: batch 1, one user, long context, device 95% idle. Ferric's existing paged-KV/radix/continuous-batching work parallelizes *across sequences* and does nothing for this. The hard part is already written and debugged: `FUSED_ATTN_WGSL` already contains the rescale (`corr = exp(m_run - m_new); l_run = l_run*corr + red[0]; accd = accd*corr + a;`) — split-KV applies that same arithmetic across partitions instead of across sequential chunks.

**Effort.** Small, one file. Dispatch `(nh, num_splits, 1)`; scratch `[nh, num_splits, dh+2]` holding unnormalized `accd`, `m_run`, `l_run`; ~30-line combine kernel. Real work is the `num_splits` heuristic — wgpu exposes no core count, so probe once or use a tuned constant, and force `num_splits=1` at short context so the extra dispatch doesn't cost more than it saves.

**Proof.** End-to-end decode tok/s at ctx = 1k / 8k / 32k on M3 Ultra (Metal), RTX 4050 (Vulkan) and headed Chrome — not a kernel microbenchmark. The measurement-discipline rule applies directly here: a kernel-isolation win means nothing if decode is weight-bandwidth-bound. Expect the win to appear only past some context length; find that crossover and gate on it. Also assert bit-identical logits vs `num_splits=1` (the combine is a different reduction order — decide explicitly whether the split path is on the byte-identical default).

### 1.2 Parameterize the WGSL kernel library and make autotuning exist in the browser — **medium effort, highest absolute value**
**What.** LlamaWeb's tunable-kernel-library idea (arXiv 2605.20706): tile size, workgroup shape, per-thread tiling and vector width become template variables in the generator, swept once per device, decisions cached per adapter.

**Why Ferric specifically.** Measured in-tree: **105 occurrences of `@compute @workgroup_size(64)`**, 16 of `(32)`, 2 of `(16,16,1)`. Nothing is parameterized, so there is nothing to search. Meanwhile `autotune_matmul` (`lib.rs:849`) is gated `#[cfg(not(target_arch = \"wasm32\"))]` — **on the browser path, where the argument for tuning is strongest and where the device is genuinely unknown until the page loads, Ferric has zero autotuning today.** Its search space is also 2 candidates (naive vs tiled) and excludes `matmul_rt`, documented in-tree as the fastest f32 GEMM on Apple Silicon; and `GEMM_CACHE` is `thread_local!`, so every page load re-pays. LlamaWeb's 41% kernel-level number is the one figure in that paper that transfers, because it was measured against \"hand-picked values chosen during development\" — precisely Ferric's current state. Their 29-33% memory and 45-69% decode figures do **not** transfer; those baselines are WebLLM/Transformers.js, which lack Ferric's paged KV and fused quant kernels.

**Cost cut.** Do not buy four vendors' GPUs to re-derive defaults. llama.cpp ships the swept answers as public macros in `ggml-webgpu-shader-lib.hpp` (`WEBGPU_MUL_MAT_TILE_M/N/K`, `WG_SIZE_M/N`, `MUL_MAT_VEC_WG_SIZE=256`, `MUL_MAT_VEC_K_Q_OUTPUTS_PER_WG=8`). Seed from those, then tune on the two machines already available. Fold in CubeCL's two published portability caveats (Vulkan/WebGPU capped at line size 4 vs 8; Metal weak on plane control) and its batch-level L2 swizzle — those are the parts of the CubeCL design that survive into WGSL.

**Effort.** Medium, three separable chunks: (a) thread tile/workgroup constants through the existing runtime WGSL codegen — this is the prerequisite and the bulk of the work; (b) un-`cfg` the tuner for wasm (`performance.now()` for `Instant`; wall-clock around submit+readback, since WebGPU gates timestamp-query and Ferric passes `timestamp_writes: None` everywhere); (c) persist *decisions* — a small adapter-keyed bucket→config blob — to OPFS/IndexedDB. **Persist decisions, not binaries:** `wgpu::PipelineCache` is Vulkan-only and WebGPU exposes no pipeline-cache object at all, so the SPIR-V-cache half of the Burn 0.21 story simply does not port.

**Proof.** Per-shape GFLOP/s vs the current hardcoded constants across Metal / Vulkan / Chrome WebGPU, then end-to-end prefill and decode tok/s. Separately measure cold-start: tuning must not regress time-to-first-token on a cache hit, and the browser cache must survive a reload.

### 1.3 Paged-attention WGSL kernel + paged KV *storage* — **large, but it is the #1 architectural gap**
**What.** mistral.rs' block-table decode attention, whose Metal implementation proves no tensor cores, no PTX and no CUTLASS are required (Apache-2.0, attribution needed).

**Why Ferric specifically.** Ferric's own source says it: `qwen3.rs:568` — \"the per-sequence work stays a loop... Paged attention is what would collapse that loop too\"; `prefix.rs` — \"wiring it in needs a paged-attention kernel, which is a separate piece of work.\" The gap is bigger than one shader: `ferric_tensor::append2` grows a **contiguous per-sequence** `KvBuf` via `reserve`, ferric-llama imports only `ferric_kv::RadixIndex`, and `PagedKv`/`BlockTable` is CPU-side bookkeeping the attention path never touches. Zero hits for `block_table` in any shader. So the GPU KV storage is not paged at all. This is the unlock for three other things: real batched decode, prefix sharing that actually saves GPU memory, and quantized KV (1.4).

**Correction to the source claim worth knowing before starting:** the MSL is a vLLM→Metal transliteration, not original, and it *does* use `simd_shuffle_xor` at 8 sites for the softmax reductions. Portability survives because the cross-warp stage already goes through threadgroup memory, so the shuffle collapses to a workgroup-memory tree reduction Ferric already writes. Budget for that, not for a surprise.

**Effort.** Large — and the shader is the *easy* half. In Ferric's favour: flash-attention prefill exists (online softmax with tiling is solved), in-shader dequant across 9+ GGUF formats is routine, and runtime WGSL codegen is the right substitute for the MSL's C++ template explosion (WGSL has no generics, so the head-size × block-size × dtype matrix must be generated). Against: two kernels are needed (v1 plus a partitioned v2 with a reduce pass), `reshape_and_cache` is mandatory, WGSL has no `reinterpret_cast` so the vectorized K loads and the awkward `x`-layout strides need manual repacking and are easy to get subtly wrong — and the real cost is the ferric-tensor storage refactor from per-seq contiguous `KvBuf` to a shared block pool, rippling through `Cache`, `append2`, `prefix.rs` and every model's attention. **Sequence it after 1.1 and 1.2** and do not start it in the same window as either.

**Proof.** Peak GPU memory at fixed batch × context vs today (measured allocation, not encoding ratio); tok/s at batch 4/8/16 vs the current `forward_batch` 2.92x-at-8-seqs baseline; and prefix-cache hit showing an actual reduction in resident KV bytes, which today it cannot.

### 1.4 Sink-aware INT8 → INT4 KV cache — **medium, rides on 1.3**
**What.** tract's `QuantizedDynKeyValueCache` design, verified at source: `KEY_BLOCK = 32` per-channel frozen block scales for Keys, per-token for Values, and `const SINK_TOKENS: usize = 4` held in f32 in both stores.

**Why Ferric specifically.** `grep` for `quantize_kv|kv_quant|int4_kv|attention_sink` across all crates returns **0**. `KvBuf` is raw f32 with no bits field and no scales. For an on-device runtime this is the difference between a 3B model fitting a 4GB GPU budget or not — a capability gap, not a speed gap. The attention-sink exception is the non-obvious part and is independently established outside tract (StreamingLLM, KIVI, the 2025 KVSink paper); tract's own \"int4 essentially lossless, ~99% top-1 on OpenELM\" figure exists only in a commit message with no committed ablation, so treat it as directionally right and re-measure.

**Two traps.** (a) It is *not* the one-line policy the summary suggests — the load-bearing part is the KIVI layout, and naive per-token key quantization with a running scale is exactly what tract's second test exists to catch. (b) **Do not copy Airframe's implementation.** Its `kv_cache.rs:106-233` allocates the full F32 K and V buffers unconditionally *and then* the packed buffers, with no `.destroy()` — net ~12.5% *more* KV VRAM, not 7x less, and its telemetry computes MB from the F32 formula in both modes so it structurally cannot show the regression. Take the shader idea (`sh_quantize_kv.wgsl`, `sh_rope_shift_int4.wgsl` shifting packed nibbles without decompressing), not the allocator.

**Proof.** Actual buffer bytes allocated, from wgpu, in both modes. Then perplexity and top-1 agreement vs f32 KV at ctx 8k and 32k — sink-on vs sink-off, because the whole design rests on that delta being real.

### 1.5 Two cheap hygiene items — **small, do them alongside anything**
- **Kill the per-dispatch uniform buffer.** `unibuf`/`uniform_u32` calls `create_buffer_init(... UNIFORM)` on every dispatch across **34 sites**. LlamaWeb's fix is one pre-allocated arena with N slots rotated round-robin. Ferric already documents the damage this causes: `ferric-core/src/lib.rs:57-64` — allocation bursts make \"Metal silently drop later buffers' contents (they read back as zeros, with no error),\" requiring a manual `flush()`. This is plausibly a latent correctness fix, not just an allocation tidy-up. **Measure it as such** (does the manual flush become unnecessary?), and do *not* claim a throughput win — Ferric's own `dispatch_vs_submit.rs` A/B recorded a 29% dispatch cut delivering 11.30 ms/token before and after.
- **Adopt the decode≡prefill equivalence gate** (Airframe `decode_gate.rs`, 229 lines, argmax + tol). Cheap, catches a bug class that only manifests token-by-token, and slots into the existing layer-exact bring-up practice. Tighten the tolerance below their 1e-2.

## 2. WORTH DOING, NOT NOW

| Item | Why not first |
|---|---|
| **MXFP4 (E2M1 + E8M0) weight format** | Genuinely missing (0 hits for `mxfp4\\|e8m0\\|e2m1\\|nvfp4\\|e4m3` in all crates) and structurally *cheap* — it is Q4_0's 32-element block layout with an exponent-shift scale (`as_type<float>(uint(e) << 23)`) and an 8-entry magnitude LUT, and Ferric already ships both halves via Q4_0 and IQ4_NL. No FP4 hardware needed. Held back only because it unlocks *new checkpoints* (GPT-OSS-class) rather than improving current ones, and it needs a new safetensors ingest path (`{name}_blocks`/`_scales`/`_bias`, 4D `[experts, out, blocks, 16]`) rather than another arm of the ggml type match. Promote this the moment a target model ships MXFP4-native. Skip the WMMA prefill kernel; the decode GEMV is the whole win. |
| **IQ4_XS / IQ4_NL GPU kernels** | `dtype.rs:808` and `:901` fall back to CPU dequant-to-f32 — an 8x memory blow-up on those formats. Small, and naturally batched with the MXFP4 work since it is the same LUT-times-block-scale shape. |
| **Relaxing naga bounds-checks on native** | LlamaWeb measured WebGPU's mandatory robustness checks at 14% decode / 23% prefill, up to 42% on some devices. Ferric forks wgpu, so this is a config change away — one of the highest information-per-hour experiments available. Not first because it is native-only (a browser tab cannot opt out), it trades away a safety net that matters more than usual for *dynamically generated* shaders, and it should ship gated off by default. Worth one measurement now, a decision later. |
| **Generic separate-draft-model speculation** | Ferric's spec decode is real, default-on, and measured (~80% d1 acceptance, `FERRIC_SPEC_DRAFT=2` → ~19% faster, d2 conditional acceptance 65-71%) — but it only works for models that ship an MTP/nextn block. Qwen3, Llama-3 and Gemma-3 get nothing. Cheaper first cut: **suffix/n-gram prompt-lookup** drafting, entirely host-side, no draft model, no training, degrades gracefully to plain autoregression. Behind 1.1-1.4 because on-device the binding constraint is memory, not decode throughput. |
| **Adaptive verify length** | Implement AdaEDL's entropy *lower bound*, not the naive \"adapt to entropy\" framing — DSpark's actual mechanism is a *trained* confidence head (`c = σ(wᵀ[h; W1[x]])` fit to `1 - ½‖p_draft − p_target‖₁`), and the literature on raw entropy is negative (ρ ∈ [−0.20, −0.15], and chat shows highest entropy *with* highest acceptance). Also unpriced by the source: variable verify width makes fp reduction order content-dependent, which is a direct cost against the byte-identical stance and ferric-certify. Small upside over the existing d1/d2 baseline; real risk. |
| **Consolidate the spec-decode driver** | It is duplicated between `examples/run_bonsai.rs` and `ferric-serve/src/main.rs:386`, runs on `qwen35::Cache` rather than ferric-kv, and is therefore single-stream and does not compose with continuous batching. Pure refactor — do it *as part of* 1.3, not before. |
| **Differentiable collectives** (`AllReduce` as an autodiff node, Burn `burn-autodiff/src/ops/distributed.rs`) | The abstraction is right and cheap (~90 lines of pure Rust) and `grep` confirms 0 hits for `all_reduce\\|collective\\|nccl` across all 17 crates — ferric-dist is pipeline-parallel *inference* only, its own header says \"capacity, not speed,\" and it measures 19.4% slower decode. But WebGPU has no P2P device memory, so every hop is map-read-to-host — precisely the path Burn measured itself 16-21x faster than — and in-browser a tab owns one device, so this becomes cross-worker messaging at ~10ms readback. Wrong scale until a training workload demands it. Also: do not copy Burn's `*mut FloatTensor` gradient swap into a `#![forbid(unsafe_code)]` crate. Note the API is churning — `burn-collective` has already been folded into `burn-backend::distributed`. |
| **OPFS weight cache + Cross-Origin Storage** | OPFS is currently only a doc comment (`ferric-web/src/stream.rs:19`); no `createSyncAccessHandle`/`FileSystemDirectoryHandle` anywhere. Ferric already has the harder half — a bounded recycling buffer pool at `ferric-tier/src/prefetch.rs:228` and HTTP-Range streaming. Small, pure UX (reload latency), zero throughput. Bundle it with 1.2's decision cache, which needs the same storage. |
| **Overlap pipeline compilation with weight loading** | Measured in-tree: 153.45 ms first-pass compile vs 0.89 ms steady, against 218 ms weight load. Saves ~150 ms of one-time startup, never a token of throughput, and the relative win *shrinks* as models get bigger. Also awkward exactly where promised — `create_compute_pipeline_async` is not on wgpu's public Rust API, only the raw wasm-bindgen bindings. |

## 3. EXPLICITLY DECLINED

**Already built — do not re-propose:**
- **Speculative decoding / MTP self-drafting.** Shipped, default-on (`ferric-serve/src/main.rs:337`), with O(1) rollback via Arc-handle cache snapshots and the rectangular causal verify kernel already written (`nn.rs:444`). The capability blurb is stale. Note Ferric's own honest number (~14% wall-clock from d2) against Google's marketed 3x — the upside here is far smaller than the ecosystem noise implies.
- **Cooperative matrix / tensor cores as a strategy.** Already built and already measured: exact on Metal (relΔ ~1e-5, 1.6-3.3x on real models), **all-zero output on Vulkan** from an unfixed naga SPIR-V codegen bug for KHR_cooperative_matrix, `unimplemented!()` on HLSL/DX12, absent from browser WebGPU. Quant-coop prefill measures **exactly 1.0x** at every M — 2-bit unpack into shared memory is the ceiling and it scales with the weight, not with M, so no batch size amortizes it. Ferric is already *ahead* of CubeCL here (whose own WGSL backend panics on `Matrix`/`CoopMma`). Also note the caught false positive: the old \"9.4/21.7 TFLOP/s NVIDIA\" figures were zero-output passes. This is an opt-in accelerator behind `FERRIC_COOP=1`, correctly gated, not a lever to pull.
- **Kernel fusion, prefix caching, continuous batching, chunked prefill, pipeline caching, GDN, sampling beyond greedy** — all present. Several sweep findings re-describe these as gaps.

**Not portable / no wgpu analogue:**
- **CubeCL's four-level matmul hierarchy** (plane specialization, barrier-driven double buffering). CubeCL's *own* WGSL compiler hard-fails on every primitive it needs: `Type::Matrix → unimplemented!(\"Matrices not yet supported in WGSL\")`, `CoopMma → panic!`, `Barrier → panic!`, `SyncPlane → panic!`. Their \"Vulkan\" is SPIR-V passthrough, not WGSL, not browser. The post contains no mention of WebGPU or WGSL at all. Their headline TFLOP figures also never disclose dtype and are ~3x the card's f32 peak, i.e. f16 tensor-core, not comparable to any WGSL f32 number. **Harvest only** the L2 swizzle, vec4 line size, and the two published caveats — fold into 1.2.
- **CUDA graph capture per batch size** (Infire, PegaInfer). `Queue::submit` takes `CommandBuffer` **by value** and consumes it; there is no compute-bundle analogue to `GPURenderBundle`; reuse is an open spec issue (gpuweb#1971). Ceiling measured anyway: 0.36 ms of a 12.37 ms token = **2.9%**, and Ferric's own A/B delivered 0.00. Independently corroborated (arXiv 2604.02344 §5.1: \"command batching, buffer pooling, and bind group caching all provide negligible benefit because autoregressive generation forces per-token sync\").
- **Green Contexts prefill/decode SM co-location.** Not \"HARD\" — **NO**. wgpu exposes one queue and no SM-partitioning primitive; there is nothing to partition.
- **MLX NAX / M5 Neural Accelerators.** Reachable only via Metal 4 TensorOps + MetalPerformancePrimitives. Ferric already has this outside wgpu (`ferric-tensor/src/metal4.rs`, ~23-31 TFLOP/s vs ~0.1 for portable WGSL matmul). Nothing further to ingest.
- **Reactant.jl / MLIR-Enzyme, ZML/Zig.** Different language stacks; no transferable artifact.
- **MLX SDPA Metal port** (via tract). Built on `simdgroup_matrix` cooperative-matrix intrinsics and Metal simd shuffles — no WGSL equivalent, and Ferric already has flash-attn prefill + fused decode + GQA/MQA + SWA. The one transferable idea from that commit is split-KV decode, which is item 1.1.

**Benefit unproven or falsified:**
- **Airframe's \"bindless\" pipeline.** Zero occurrences of `binding_array`/`BUFFER_BINDING_ARRAY` in the crate; their own docs describe a mega-buffer plus an offsets uniform, split into 3 blobs for the 128MB binding limit. The \"near-linear scaling with context length\" quote is about *KV memory*, not throughput, and there is no A/B. The premise (\"bind-group churn is the classic wgpu decode bottleneck\") contradicts their own doc — \"weight reads dominate\" — and Ferric's roofline data.
- **Luminal's e-graph search compiler.** The mechanism ships, but: the \"~80% of theoretical max on H100\" figure appears once in README prose with no benchmark (and \"public benchmarking suite\" is still an unchecked roadmap box); the search space *contains* cuBLASLt rewrite rules and a FlashInfer JIT, so it schedules around vendor kernels rather than beating them — inverting the \"WGSL has no cuBLAS to lose to\" argument; the \"rediscovers FlashAttention\" claim has no test or artifact; extraction is a *stochastic genetic* search, not exhaustive; a 10-min-to-10-hour search cannot run in a tab (and Chrome quantizes timestamp-query to 100 µs); and their own `LessonsLearned.md` documents a nondeterministic whole-graph Llama-3.1-8B miscompile because measured latency is an honest cost function and a completely dishonest correctness function. **Take exactly one thing for free:** any autotuner candidate must be validated against a reference execution. Fold that into 1.2.
- **Batch-invariant kernels.** LLM-42 measures the cost: 63% slower GEMM, up to 50% on RMSNorm, 56% system throughput collapse when one deterministic request joins normal traffic. Ferric gets its determinism structurally, from fixed kernels and fixed reduction order, not from a runtime mode. Do not adopt the flag; do keep the awareness that split-KV (1.1) and adaptive verify length both introduce batch/content-dependent reduction order.

**Wrong scale for an on-device runtime:** FP8 attention on Hopper/Blackwell, NVFP4 serving formats, FlashAttention-4 (requires Hopper+), FlashInfer, disaggregated prefill/decode + MoRI-IO, RDMA/Mooncake KV transport, L3 distributed tiered KV, 8-GPU expert parallelism, Marlin INT4, per-batch-size CUDA graphs. These are datacenter economics. The single-node, single-tab, one-user regime is a *different machine*, and importing its techniques costs effort with no reachable payoff.

## 4. LANDSCAPE SHIFTS — positioning, not features

**The niche did not stay empty, but it split, and Ferric's half is still its own.**

1. **The natural incumbent died; a stronger one arrived.** HuggingFace's `ratchet` — the WebGPU-first Rust runtime in Ferric's exact niche — is effectively abandoned (last substantive commit 2024-11-23; `ratchet-core` 1.2.1 since 2024-09-30; the only 2026 activity is a CI chore). But `ggml-webgpu`/LlamaWeb (UCSC + Tyler Sorensen, *not* Microsoft Research as widely reported) landed via 100+ PRs, 8,470 lines of C++ plus 44 WGSL template files, 72 operators, 23 formats, and is under continuous merge with Gerganov promoting it. **\"Browser WebGPU LLM inference\" is no longer unoccupied ground, and it now has llama.cpp's ecosystem gravity behind it.** Ferric can no longer claim the category by default; it has to claim a property inside it.

2. **The closest pure-Rust twin cannot run in a browser.** Airframe/Shimmy (38,725 lines Rust, 15 WGSL shaders, no llama.cpp) is a real pure-Rust WGSL GGUF engine — and contains **zero** `wasm32`/`wasm-bindgen`/`web-sys`. It is native-only and has never run in a tab. Meanwhile CubeCL's WGSL backend `panic!`s on matrices, cooperative MMA, barriers and plane sync. So the intersection **pure Rust ∩ one codebase ∩ native *and* browser** is still Ferric alone. That intersection — not \"WebGPU inference,\" not \"Rust inference\" — is the defensible sentence.

3. **The browser now ships its own model.** Chrome 148 (May 2026) shipped the Prompt API and Gemini Nano to stable by default, plus Summarizer/Translator/Language Detector; Google released LiteRT.js and put MediaPipe's LLM Inference API into maintenance. **\"You can run an LLM in a browser tab\" stopped being a differentiator in 2026.** What is left, and what Ferric actually has: *which* model (any GGUF, not one vendor-gated 2.7-4 GB blob behind a 22 GB disk / 16 GB RAM gate), determinism, verifiability, weight streaming for models larger than RAM, and training in the same stack. Lead with model sovereignty and certification, not with \"in the browser.\"

4. **Verifiability is being claimed by others — but only the weak version.** Airframe ships a 5-gate \"numerical certification pipeline.\" Read closely, those are regression tests against a reference on specific inputs at 1e-2 tolerance, and Gate 3 (\"dual-peel self-consistency\") just runs the same thing twice, catching nondeterminism rather than correctness. `ferric-certify` is branch-and-bound interval verification proving a property holds *everywhere* in a continuous region or returning a counterexample — a soundness proof, a different axis entirely. **Nobody else in this sweep has soundness.** But the word \"certification\" is now being used by a direct peer, so the distinction has to be stated explicitly and early or it will be flattened. This is the one place where positioning work is more urgent than engineering work.

5. **Portable-runtime independence just changed hands.** Qualcomm completed its acquisition of Modular on 2026-07-29 (~$4B); Lattner becomes EVP at a hardware vendor. Mojo hit 1.0 beta with an open-source-at-1.0 commitment, but the neutral-portability story is now owned by a silicon company. ZML/LLMD (Zig, $20M, 2026-07-08) is the other multi-backend contender and is server-side only. **The \"vendor-neutral portable AI runtime, owned by nobody\" position is more open in late 2026 than it was in early 2026** — and an open pure-Rust stack is a more credible occupant of it than a chip vendor's language. Worth saying out loud.

6. **The frontier moved somewhere Ferric should decline to follow.** Nearly everything shipping in 2026 — DFlash/DSpark, DeepSeek Sparse Attention, MTP heads in-checkpoint, NVFP4/MXFP4 serving, disaggregated prefill/decode, tiered L3 KV, backend sampling, tensor parallelism — is datacenter throughput engineering. Chasing parity there is unwinnable and off-thesis. The on-device constraint set is *memory, first-token latency, and joules*, and it selects a different, much shorter list: quantized KV, weight streaming, split-KV decode, per-device tuning, format coverage. Every item in §1 is on that list. **Frame the roadmap as a different objective function, not as a lagging subset of vLLM's.**

7. **One genuinely new format shift to track, not chase.** MXFP4/NVFP4 are now *native checkpoint* formats, not runtime compression — gpt-oss was trained in MXFP4, and ggml has assigned type IDs 39/40. Ferric has zero code for either. That is a *reachability* risk (models it cannot load), separate from performance, and it is the one thing in §2 that should be promoted to §1 on a specific trigger: the first model you actually want to run shipping MXFP4-native.

**One-line verdict:** the thesis holds, but its uncontested part narrowed from \"WebGPU LLM runtime\" to \"one pure-Rust stack, native *and* browser, with sound verification and model sovereignty.\" Two competitors now own adjacent halves — LlamaWeb owns browser-WebGPU-with-C++, Airframe owns pure-Rust-native — and neither can cross into the other's half. Ferric spans both. Say that, and then make it true on the tuning axis (§1.2), because that is the axis LlamaWeb published a 41% lead on against exactly the constants Ferric has hardcoded 105 times."
